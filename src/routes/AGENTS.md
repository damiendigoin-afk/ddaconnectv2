# Route and workflow rules (src/routes, document and order flows from src/lib)
- Tour tire reading is local OCR only (tesseract.js, src/lib/tire-ocr.browser.ts + src/lib/tire-ocr-parse.ts); analyzeWheelPhotos is a no-op. The separate « État pneus » (route /etape-pneu, rules src/lib/tire-step.ts) is the only tire AI flow, via runPaidAi feature tire_step; its depth is an explicitly labelled experimental estimate. Why: AI vision only where the user explicitly asked for it.
- Document reading (photo/PDF) always goes through the common pipeline: browser `localDocText` (src/lib/doc-text.browser.ts, pdf text or Tesseract) -> deterministic rules (src/lib/doc-rules.ts) -> `readDocument` (src/lib/doc-pipeline.server.ts): AI text fallback, then vision, only if business-quality required fields are missing; `fallback_ai_enabled` gates text-AI and text-PDF fallback, while real photos / scanned PDFs (detectMedia) always get essential vision (budgets still apply); every AI call goes through runPaidAi (gated + route logged). Purchase and expense photos/scans are vision-first (one essential pass, OCR only fills reliable missing fields); expense extracts then pass `expense-validate.ts`, with visible correction/confirmation and a manager guard before accounting. Carrefour CLIPRO/CLIP PRO/CLI PRO sets En compte only beside explicit payment wording (`expense-payment.ts`), never selects Direction/VO/Atelier, and never overrides a user's payment correction. Other kinds keep rules-first. Purchase-document photos (readPurchaseDoc) also skip local OCR; Tesseract runs only as fallback when vision is unusable (server `fallbackOcr`, forced review), and the original upload (prepareSupplierDocFile) runs in parallel without creating the inbox row. Why: plausible but wrong OCR must not block visual correction; minimise AI credits, one place for the rule.
- OR WinMotor scanné/saisi à l'Atelier : lecture complète OR papier (ocrRepairOrder, règles repairOrderRules) puis RPC ensure_winmotor_dossier_full (clé site_id + or_number ; véhicule par plaque > VIN > historique WinMotor ; client lié > e-mail > téléphone ; champs vides complétés, conflits renvoyés et appliqués seulement via apply_dossier_conflict). Why: comportement V2 sans jamais générer de n° OR ni écraser silencieusement.
- Document source d'une commande : original unique dans dda-media/fournisseurs (bucket privé, policy storage_object_owned par site), métadonnées dans inbox_documents (hash SHA-256 => stockage réutilisé), part_orders.source_document_id ; ouverture par URL signée 5 min (src/lib/order-docs.ts, règles order-docs-rules.ts). Jamais de suppression à l'annulation. Why: rouvrir le PDF/photo d'origine sans base64 en base.
- Commande existante modifiée uniquement via RPC SECURITY DEFINER update_part_order (même ID/lignes, lignes reçues/facturées : réf/type figés, qté ≥ reçu, pas de suppression ; historique avant/après dans parts_events 'manual_edit'), miroir pur src/lib/order-edit-rules.ts. Why: correction après validation sans casser stock ni factures.
- Scan OR : lecture validée par src/lib/or-scan-validate.ts (plaque SIV/FNI, jamais = n° OR/compte ; modèle pollué retiré ; marque/modèle incohérents = suspect => relecture vision ; deux lectures de plaque à 1 caractère = doute) ; écran OrScanConfirm seulement en cas de doute ; ensure_winmotor_dossier_full refuse une plaque atypique non confirmée (plate_confirmed) ; journal privé or_scan_logs + bucket or-scans (30 j, purge applicative, gérant/URL 5 min) ; banc vision isolé runOrScanBench avec accord. Why: plaque 50690, RENAULT CEED, modèle pollué, sans saisie systématique.
- Photos annotées État pneus -> devis : rendu canvas de la vraie photo (tread-annotate.browser.ts), transmis par sessionStorage QUOTE_PHOTOS_KEY, 2e page du PDF ; historique véhicule lu par tireStepHistory (RLS + URL signées 5 min). Why: aucune image IA, aucune migration.
- Bon de commande Renault « Détail de commande » : parser dédié renaultOrderDetailRules (doc-rules, colonnes PDF.js re-découpées) ; fournisseur = Distributeur, PA = montant HT de droite (jamais Prix client). Lecture incomplète => une seule passe vision Gemini 3.8 Flash dédiée (src/lib/renault-order.ts, hors réglage repli IA), fusion par référence sans écraser un PA cohérent. Why: format fréquent, doit sortir complet sans saisie.
- Agent WINmotor local piloté uniquement via RPC winmotor_agent_status / winmotor_enqueue_job et lecture RLS de winmotor_agent_jobs (src/lib/winmotor-agent.ts, route /winmotor) ; commandes UI limitées à celles exécutées par l'agent (PING, GET_OR). Why: backend existant réutilisé, aucun effet sur les imports WinMotor.
- Expédition ≠ réception : un BL/facture/avis rapproché alimente seulement part_order_lines.qty_shipped via RPC SECURITY DEFINER record_part_shipment (table part_order_shipments, idempotente par document+ligne) ; « Reçue maintenant » est prérempli (receiptPrefillQty : qté du document rapproché → reliquat expédié → reliquat commandé, plafonné au reliquat) mais rien n'est enregistré avant le clic « Réceptionner » ; seule la confirmation physique (validateReceipt / receiveAllShipped) crée réception, stock et affectation OR. Statut « Expédiée » dérivé (src/lib/shipment-rules.ts), statuts DB inchangés. Why: un document d'expédition ne prouve pas l'arrivée au garage.
- Champs libres OR (requested_work, client_remarks) : zonage strict sous leur libellé, la première ligne étrangère (isOrFreeTextForeign : branding, conseiller, bloc client, adresse, tél., e-mail, libellé) ferme la zone ; même filtre appliqué aux réponses IA dans sanitizeRepairOrder ; zone vide => null. Why: OR 50864, slogan/bloc client dans « Travaux prévus ».
- Commande simplifiée sans ligne (isBareSimplified, src/lib/parts-site.ts) : fournisseur identique + OR/repère exact (repair_orders.or_number ou requested_or_number) suffit, sans réf/qté/prix ; plusieurs candidates = ambiguïté, jamais de choix. Le BL complète la même commande (completeSimplifiedOrder / simplifiedEnrichment). Commandes détaillées : critères inchangés. Why: BL CAZES 50912.
- BL ↔ commande simplifiée sans lignes : fournisseur + (OR exact OU immat exacte, directe ou via repair_orders du véhicule = plate_or_numbers) suffit ; lignes « brut/remise/net » lues par parseDiscountLines (PA = net) ; lecture incohérente => _suspect (vision). Why: BL CAZES 432112 / OR 50912.
- Commande → OR atelier : RPC SECURITY DEFINER sync_part_order_or / sync_or_part_orders (repère OR unique du site via resolve_or_for_order, jamais autre site ni ambigu) posent repair_order_id et affectent les lignes reçues en or_part_usage « pending » (allocate_to_or, une seule fois par receipt_line_id) ; appelées après validateReceipt et à l'ouverture de l'OR. Why: OR 50912 restait « Aucune commande ».
- Scan OR : résolution de OrScanConfirm dans src/lib/or-scan-confirm.ts (champs retenus VIN/MEC appliqués avant recalcul des doutes ; case « J’ai vérifié » réservée à plaque/client/marque-modèle ; conflit MEC levé par radio ou saisie manuelle valide). VIN normalisé via src/lib/vin.ts (O->0 seul, I/Q jamais corrigés, brute en vin_ocr_raw) ; VIN divergent = choix exclusif Ixellio/scan OR (applyVehicleSource : VIN, MEC, marque, modèle seulement, jamais vide) avant tout enrichissement. Why: GM-634-SG, fausse alerte VIN O/0 et cases ambiguës.
