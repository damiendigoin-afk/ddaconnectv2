# Domain rules (src/lib)
- Phase B stock: stock levels are derived only from `stock_movements` deltas (view `stock_levels`); rules live in src/lib/parts-rules.ts. Why: traceable, physical-only stock, testable.
- WinMotor invoices: imported only via SECURITY DEFINER RPCs wm_* (site chosen explicitly, OR identity = site + or_number, or_sale_final once per link). Why: WinMotor primacy, idempotent re-imports, traceable stock.
- Supplier real cost: invoice lines link to receipt lines via supplier_cost_lines (src/lib/supplier-cost.ts); only valuation (PAMP, last PA, unit_cost_real) changes, never quantities. Why: physical stock ≠ financial documents, idempotent re-control.
- Pièces & achats follows the global active site (TopBar ActivePicker → usePartsCtx writeSite/readSite, rules in src/lib/parts-site.ts); no per-screen site selectors. Why: one site at a time, never write silently on the other company.
- Tour tire quotes persist one grouped quote line per axle group with seven offer snapshots in computation; only selected_slot contributes to totals. Why: preserve the shared tire engine while preventing duplicate wheel lines.
- Tire monte is consolidated per wheel then per axle (src/lib/tire-axle.ts: all wheels incl. OK, conflicts block fusion, never copied across axles); tier slots fall back through active brands in sort_order. Why: more photos = more reliable monte, no empty slots when the default brand lacks stock.
- Tour tire reading is local OCR only (tesseract.js, src/lib/tire-ocr.browser.ts + src/lib/tire-ocr-parse.ts); analyzeWheelPhotos is a no-op. The separate « État pneus » (route /etape-pneu, rules src/lib/tire-step.ts) is the only tire AI flow, via runPaidAi feature tire_step; its depth is an explicitly labelled experimental estimate. Why: AI vision only where the user explicitly asked for it.
- AI daily budget is single and shared: ai_budget_settings.daily_credits (Coûts et IA), counted over all features from Paris midnight (src/lib/ai-budget-day.ts); ai_bench_settings.daily_credits is deprecated. Why: a hidden bench budget (default 3) blocked tests.
- Storage dda-media `fournisseurs/`: active users with module `magasin` may upload unlinked files; linked files readable only if the inbox_documents site is accessible (storage_object_owned). Why: non-managers were blocked by the manager-only ELSE branch.
- Supplier identification happens at document import (src/lib/supplier-identify.ts + DocSupplierLink): found => extracted.supplier_id, unknown => prefilled quick create, ambiguous => manual pick; reception-time ensureSupplierByName is only a safety net. Why: no receipt/document left with "Fournisseur ?".
- Receipt/order cancellation only via SECURITY DEFINER RPCs cancel_part_receipt / cancel_part_order (status cancelled + who/when/why, exact reversal movements linked by reversal_of, no DELETE); pure mirror in src/lib/parts-rules.ts. Why: traceable undo, never double-reversed.
- Order supplier fix/edit via setOrderSupplier (src/lib/parts.ts) + OrderSupplierFix: updates part_orders.supplier_id and inbox_documents.extracted.supplier_id together. Why: no order left 'Fournisseur à préciser' when the source doc names one.
- Document reading (photo/PDF) always goes through the common pipeline: browser `localDocText` (src/lib/doc-text.browser.ts, pdf text or Tesseract) -> deterministic rules (src/lib/doc-rules.ts) -> `readDocument` (src/lib/doc-pipeline.server.ts): AI text fallback, then vision, only if business-quality required fields are missing; `fallback_ai_enabled` gates text-AI and text-PDF fallback, while real photos / scanned PDFs (detectMedia) always get essential vision (budgets still apply); every AI call goes through runPaidAi (gated + route logged). Why: minimise AI credits, one place for the rule.
- OR WinMotor scanné/saisi à l'Atelier : lecture complète OR papier (ocrRepairOrder, règles repairOrderRules) puis RPC ensure_winmotor_dossier_full (clé site_id + or_number ; véhicule par plaque > VIN > historique WinMotor ; client lié > e-mail > téléphone ; champs vides complétés, conflits renvoyés et appliqués seulement via apply_dossier_conflict). Why: comportement V2 sans jamais générer de n° OR ni écraser silencieusement.
- Document ajouté après coup à une réception (src/lib/receipt-docs.ts, règles pures receipt-docs-rules.ts) : inbox_documents.linked_kind='part_receipt' + source_document_id si vide ; jamais de ligne ni de mouvement de stock. Why: enrichissement documentaire sans double réception.
- Documents d'achat : lecture partielle maximale ; OR/immat jamais prérequis ; alias fournisseur persistants ; rapprochement n° commande > OR > immat > réf > contenu > fournisseur. Le contrat normalisé accepte les clés document et formulaire pour rester idempotent. Why: aucun double passage serveur+navigateur ne doit vider les lignes.
- Prix saisis (PA HT…) via PriceInput (src/lib/price-input.ts) : frappe libre virgule/point, conversion au blur seulement. Why: champ numérique contrôlé empêchait de taper « , » / « . ».
- Commande fournisseur : part_orders.order_date = date de commande (doc via orderDate() de doc-rules, jamais « Payée le » ; défaut date du jour locale). Fournisseur cherché aussi en pied de page (footerSupplierName). Why: commande PAD 2887082.
- Document source d'une commande : original unique dans dda-media/fournisseurs (bucket privé, policy storage_object_owned par site), métadonnées dans inbox_documents (hash SHA-256 => stockage réutilisé), part_orders.source_document_id ; ouverture par URL signée 5 min (src/lib/order-docs.ts, règles order-docs-rules.ts). Jamais de suppression à l'annulation. Why: rouvrir le PDF/photo d'origine sans base64 en base.
- Commande existante modifiée uniquement via RPC SECURITY DEFINER update_part_order (même ID/lignes, lignes reçues/facturées : réf/type figés, qté ≥ reçu, pas de suppression ; historique avant/après dans parts_events 'manual_edit'), miroir pur src/lib/order-edit-rules.ts. Why: correction après validation sans casser stock ni factures.
- Rapprochement réception BL ↔ commande : fournisseur identique (sameSupplier, src/lib/parts-site.ts) = filtre bloquant ; fournisseur incertain => confirmation avant toute suggestion ; sans OR/immat, référence exacte exigée ; désignation seule jamais candidate ; prix = contrôle d écart. Why: faux rapprochements entre agences Faurie Sarlat/Bergerac.
- BL multi-commandes : répartition pure dans src/lib/multi-order-reception.ts (fournisseur identique bloquant, réf exacte ligne par ligne parmi reliquats, ambiguïté = choix utilisateur) ; validateMultiReceipt crée une réception par commande avec le même source_document_id, idempotente par (document, commande). Why: part_receipts n a qu un order_id ; jamais de doublon.
- Immatriculations lues (OCR ou IA) passent par strictPlate (src/lib/plate.ts) dans sanitizeRepairOrder : correction seulement si unique, sinon rejet = champ manquant ; modèle véhicule validé par isPlausibleModel. Why: EMA426NG et n° compte pris pour le modèle.
- Photos annotées État pneus -> devis : rendu canvas de la vraie photo (tread-annotate.browser.ts), transmis par sessionStorage QUOTE_PHOTOS_KEY, 2e page du PDF ; historique véhicule lu par tireStepHistory (RLS + URL signées 5 min). Why: aucune image IA, aucune migration.
- Bon de commande Renault « Détail de commande » : parser dédié renaultOrderDetailRules (doc-rules, colonnes PDF.js re-découpées) ; fournisseur = Distributeur, PA = montant HT de droite (jamais Prix client). Lecture incomplète => une seule passe vision Gemini 3.8 Flash dédiée (src/lib/renault-order.ts, hors réglage repli IA), fusion par référence sans écraser un PA cohérent. Why: format fréquent, doit sortir complet sans saisie.
- Commandes : seul le RDV (appointment_date, facultatif) est saisi/affiché ; alerte J-1/J0 non reçue dans src/lib/order-logistics.ts (jamais bloquante) ; expected_delivery_date conservée en base mais masquée ; order_date automatique. Fournisseurs les plus utilisés = rankSuppliers (demi-vie 60 j). Why: simplicité front office.
